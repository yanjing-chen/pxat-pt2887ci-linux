# Windows 指纹驱动包逆向分析报告

对象：厂商 Windows 指纹驱动包 `06_Fingerprint.zip`（06OMS 1.0.0.29）
目标：为 Linux 上的指纹模块开发可用驱动
环境：Ubuntu 系 `libfprint 1:1.95.2+tod1-1ubuntu2`，fprintd 1.94.5
日期：2026-11-13

---

## 一、包结构：其实是两套互不相关的驱动

外层 zip 里只有一个内层 zip，解开后：

```
06OMS_1.0.0.29_PixelAuth_3.0.29.0.zip
├── Install.bat                 pnputil /add-driver *.inf /subdirs /i
├── OMS/                       ← 驱动栈 A
│   ├── OMSFpDriver.inf        USB\VID_33A7&PID_2388
│   ├── OMSFpDriver.dll        UMDF WBDI 驱动
│   ├── OMSEngineAdapter.dll   WinBio 厂商引擎适配器
│   ├── OMSFPServer.exe        服务
│   ├── ACM32FP.bin            固件（202 KB）
│   ├── config.ini             FW_VERSION=acm32_btl_ofilm_pc_000057
│   └── omsfpdriver.cat
└── PixelAuth/                 ← 驱动栈 B
    ├── WBFBioUSB.inf          USB\VID_2F0A&PID_...（6 个 PID）
    ├── WBFBioUSB.dll          2.3 MB，UMDF WBDI 驱动（含固件字符串）
    ├── SensorAdapter.dll      WinBio 传感器适配器
    ├── EngineAdapter.dll      引擎适配器
    ├── StorageAdapter.dll     存储适配器
    ├── BioInitService.exe     初始化服务
    ├── BioInit.dat           内容仅一个字节 0x31
    ├── devcon.exe / tracelog.exe
    └── wbfbiousb.cat
```

`Install.bat` 只是把两个 `.inf` 都塞给 `pnputil`，说明这是**同一机型可能搭配的不同模组**
的合集安装包，装哪个由硬件 ID 决定。

### INF 里的硬件 ID

`OMS/OMSFpDriver.inf`（UTF-16LE）：

```
ManufacturerName = "Jiangxi OMS Microelectronics Co.,Ltd."
%WBDIUsbDeviceName% = Biometric_Install, USB\VID_33A7&PID_2388
UmdfDispatcher = NativeUSB
EngineAdapterBinary = "OMSEngineAdapter.dll"
```

`PixelAuth/WBFBioUSB.inf`（UTF-16LE 带 BOM）：

```
DriverVer = 03/13/2024, 3.0.29.0
USB\VID_2F0A&PID_100B
USB\VID_2F0A&PID_1021
USB\VID_2F0A&PID_1055          ← 本机
USB\VID_2F0A&PID_1059&REV_0001&MI_00
USB\VID_2F0A&PID_100D&REV_0001&MI_00
USB\VID_2F0A&PID_100E
SensorAdapterBinary  = SensorAdapter.DLL    （厂商自定义）
EngineAdapterBinary  = EngineAdapter.DLL
StorageAdapterBinary = StorageAdapter.DLL
UmdfDispatcher       = NativeUSB
HKR,"WBFBioUSB","UpdateFirmwareCount", 3
```

两套 INF 都是 **Windows Biometric Framework / WBDI 用户态（UMDF）驱动**，
`Class=Biometric`，`ClassGuid={53D29EF7-...}`。也就是说
**Windows 侧没有内核驱动，真正的通信逻辑全在 `.dll` 里**——这对逆向是有利的：
没有 `.sys` 的 IOCTL 黑盒，协议帧直接出现在 DLL 的常量里。

## 二、本机到底装的是哪一颗

```
$ lsusb -d 2f0a:1055
Bus 001 Device 003: ID 2f0a:1055 PXAT PT2887-CI Module
```

`lsusb -v -d 2f0a:1055`：

| 字段 | 值 |
|---|---|
| `idVendor / idProduct` | `0x2f0a / 0x1055` |
| `bcdUSB` | 2.00 |
| `bcdDevice` | 30.56 |
| `iManufacturer` / `iProduct` | `PXAT` / `PT2887-CI Module` |
| `iSerial` | 序列号（涉及个人设备，此处隐去） |
| `bDeviceClass` | `0xff` Vendor Specific |
| `bNumConfigurations` | 1，`bNumInterfaces` 1 |
| `bInterfaceClass` | `0xff` |
| `EP 0x81` | Bulk **IN**，`wMaxPacketSize 0x0040` |
| `EP 0x02` | Bulk **OUT**，`wMaxPacketSize 0x0040` |
| 速度 | Full Speed (12 Mbps) |

结论：**本机用的是 PixelAuth 栈（栈 B），PID 1055 正好在 INF 列表里**。
`OMS/` 那套（`33A7:2388`、ACM32 固件、ofilm 版本号）是另一款模组，本机没有，
开发时不应混入。这个区分很重要——如果照着 `OMSFpDriver.dll` 的
`IOCTL_OMS_*` / `BulkReadPipe` 去实现协议，方向就完全错了。

另外本机已装 `libfprint-2-tod1`（Ubuntu 的 TOD 分支）和 fprintd，
`fprintd-list` 原本返回 `No devices available`，说明只缺一个匹配的驱动 `.so`。

## 三、从 `WBFBioUSB.dll` 里把协议挖出来

DLL 是 x86-64 PE，2.3 MB。用 `strings` 先扫一遍，出现了这些可疑内容：

```
PXAT                       （6 处）
PT2887-CI Module           ← 明确点名本机型号
CMDSET_UKEYEX / CMDSET_BINSTREAM / CMDSET_SMODULEBIN / CMDSET_SMODULE
ep_init_sensor fail %x %x
==== Dump OTP 0x10~0x20:
flash_spi_cmd: %d
ep0ack
slot full / enroll / index / verify
```

后半段 `flash_spi_cmd`、`(addr >= 0x80000000)`、`pxNewBlockLink` 这类断言
说明 DLL 里**内嵌了一段芯片固件镜像**（FreeRTOS 风格断言），
`CMDSET_*` 是固件的升级命令集。这解释了为什么 DLL 有 2.3 MB。

### 3.1 硬编码的 PXAT 命令帧

在文件偏移 `0x8b184` 处，编译器用一串 `mov [rbp+N], imm32` 在栈上拼帧：

```
c7 45 0f 50 58 41 54     mov [rbp+0x0f], 0x54584150   ; "PXAT"
c7 45 13 c0 00 0b ef     mov [rbp+0x13], 0xef0b00c0   ; c0 | len=0x000b | ef
...
c7 45 17 01 ff ff 00     ...
c7 45 1b 00 00 01 a1     ...                          ; plen=01, cmd=a1
66 c7 45 1f b4 83        mov word [rbp+0x1f], 0x83b4  ; CRC
```

拼出来是：

```
50 58 41 54 c0 00 0b ef 01 ff ff 00 00 00 01 a1 b4 83
```

按字节解读：

| 偏移 | 字节 | 含义 |
|---|---|---|
| 0..3 | `50 58 41 54` | 魔数 `"PXAT"` |
| 4 | `c0` | 固定 |
| 5..6 | `00 0b` | BE16 内层长度 = 11 |
| 7..13 | `ef 01 ff ff 00 00 00` | 固定前缀（7 字节） |
| 14 | `01` | payload 长度 |
| 15 | `a1` | 命令：读设备信息 |
| 16..17 | `b4 83` | BE16 CRC |

`inner_len = 11 = 7 (前缀) + 1 (长度字节) + 1 (payload) + 2 (CRC)` ——
**包含 CRC 的 2 字节**。这一点是这套协议最容易踩的坑：漏算就只回 NAK。

### 3.2 CRC 算法验证

试 CRC-16/KERMIT（poly 0x1021，init 0，refin/refout = true，xorout 0）：

```
CRC-16/KERMIT( { a1 } ) = 0xb483
```

与 DLL 里的 `b4 83` **完全一致**，帧格式和校验算法同时得到确认。
这条验证也直接写进了 `pxat_probe frames` 自检。

### 3.3 第二条命令、NAK、以及型号字符串

| 文件偏移 | 内容 | 意义 |
|---|---|---|
| `0x8b1b4` | `50 58 41 54 c0 00 1b ef 01 ff ff 00 00 00 11 a2 …` | 命令 `a2`，payload 17 字节（运行时填充），`inner=0x1b=27=10+17` ✓ |
| `0x196cb8` | `PXAT\0\0\0\0` 紧跟 `PT2887-CI Module\0` | DLL 明确面向本机型号 |
| `0x197478` | `50 58 41 54 c0 00 02 9f ff` | 9 字节 NAK，与社区 PXAT 笔记里记录的 NAK 一模一样 |
| `0x16a2a8` / `0x199af8` | `PXAT` 作为 CMDSET 表的标签 | 固件升级命令集 |

`a2` 是一条 17 字节载荷的配置/初始化命令，具体字段未在静态分析里还原。
日常「读索引 → 验证 → 录入」不依赖它，因此驱动未实现；
如 `selftest` 通过但录入异常，可以用探针的 `raw --unsafe a2 ...` 继续探测。

### 3.4 与社区实测笔记交叉印证

社区项目 `dancingonmoon/pixelauth-pt2887-linux`（MIT）用 usbmon 抓过同厂
`2f0a:8020 PT2887-SS` 的真实流量，其 `docs/protocol-pxat.md` 给出的帧格式、
NAK、命令表和状态码，与上面从**本机厂商 DLL** 里挖到的字节全部吻合。
两边一个来自实机抓包、一个来自厂商二进制，互为独立印证：

> `PT2887-CI (2f0a:1055)` 与 `PT2887-SS (2f0a:8020)` 使用同一套 PXAT bulk 协议。

## 四、完整协议表

**端点**：`0x02 OUT` / `0x81 IN`，bulk，64 字节包。

| 命令 | payload | 作用 |
|---|---|---|
| `a1` | — | 设备信息，39 B（末尾 16 字符 = SN） |
| `1f` | — | 读索引表，33 B = 1 字节状态 + 32 字节位图（256 槽位，LSB 优先） |
| `a6` | `a6 <addr BE16> 00 40` | 读 64 B 记录，`addr = slot × 0x40` |
| `a5` | `a5 <addr BE16> 00 40 <00> <slot LE16> <20> <32B UUID> <28B 零>` | 写 64 B 记录，payload 共 69 B |
| `f2` | — | 准备 / arm（也是 abort 的前缀） |
| `33` | `33 <slot>` | **定向验证一个槽位**（芯片不做 1:N） |
| `31` | `31 <slot BE16> 0f 00 00` | 启动录入 |
| `0c` | `0c <slot BE16> 00 01` | 删除（只清索引位，**不可逆**） |
| `f1` | — | 轮询当前操作 |
| `f4` | — | 中止，**必须紧跟在 `f2` 之后**，单发无效 |

**验证状态**：`f0` 等手指 · `f1` 匹配成功（后跟 `<slot BE16><score BE16>`，满分 100）·
`f2` 按下但不匹配（粘滞）· `f3` 空闲/取消 · `f4` 罕见。

**录入状态**：`e0` 等手指 · `e4` 手指放下 · `eb` 采集中 · `e6` 本次图像被拒（继续）·
`e1` **完成** · `f3` 取消。除 `e1` 外所有状态都要继续轮询。

**三个关键行为**

1. 芯片一次只比一个槽位；所谓 1:N 要主机循环，每换一个槽位重新 `f2 → 33 <slot>`。
2. 重新 arm 会重置「手指落下」边沿检测 —— 循环时用户必须抬手重按，一直按着后面全是 `f0`。
3. 录入成功后**必须发 `a5`** 写 32 字节主机 UUID（芯片只做 `memcmp`，不是模板/哈希）。
   不写的话记录区留 `0x33` 占位符，这枚指纹永远验不过。

## 五、驱动设计要点

形态选的是 **libfprint TOD 树外驱动**，因为：

- 本机 `libfprint-2-tod1` 已装，`/usr/lib/x86_64-linux-gnu/libfprint-2-tod.so.1`
  里编译进了 `/usr/lib/x86_64-linux-gnu/libfprint-2/tod-1`，并支持
  `FP_TOD_DRIVERS_DIR` 覆盖；
- `fprintd` 同时链接 `libfprint-2.so.2` 和 `libfprint-2-tod.so.1`；
- 设备是 vendor-specific bulk，用 `FpiUsbTransfer` 的异步 bulk 收发最自然；
- 不动内核、不动系统包，安装/回滚都只是一个 `.so` 文件。

驱动导出唯一符号 `fpi_tod_shared_driver_get_type()`，`class_init` 里注册：

```
id                 = "pxat_pt2887ci"
full_name          = "PXAT PT2887-CI Fingerprint Sensor"
id_table           = { 2f0a:1055 }
scan_type          = FP_SCAN_TYPE_PRESS
nr_enroll_stages   = 14
features           = STORAGE | STORAGE_LIST | STORAGE_DELETE | STORAGE_CLEAR | DUPLICATES_CHECK
callbacks          = probe open close cancel verify identify enroll list delete clear_storage
```

`FP_DEVICE_FEATURE_STORAGE` 必须显式声明，否则 `fp_device_list_prints()` 会在入口
直接返回 "Device has no storage"。`DUPLICATES_CHECK` 也必须声明，
否则 libfprint 会在录入前跑通用去重检查，而对 match-on-chip 设备来说模板本来就在芯片里，
必然误判导致录入永远进不去。

`FpPrint` 用 `fpi-data = GVariant(uint32(slot))` 承载槽位号。
RAW 类型**必须有数据体**，否则 `fp_print_serialize()` 不解引用判空，fprintd 存盘会段错误。

`cancel` 置一个软标志让轮询循环 200 ms 内收尾（空实现会让 GNOME 取消按钮转圈 29 秒）。
`close` 统一发 `f2 → f4`，否则芯片停在武装态、指示灯常亮且 USB 复位清不掉。

槽位区间默认 **10..19**，可用 `PXAT_SLOT_MIN` / `PXAT_SLOT_MAX` 覆盖。

## 六、验证结果（本次会话内实际跑过的）

| # | 检查 | 结果 |
|---|---|---|
| 1 | 帧 + CRC 自检 `pxat_probe frames` | 生成 `50 58 41 54 c0 00 0b ef 01 ff ff 00 00 00 01 a1 b4 83`，与 DLL `0x8b184` 逐字节一致 |
| 2 | `.so` 导出符号 | `fpi_tod_shared_driver_get_type` 存在 |
| 3 | 运行时类注册 `check_driver` | `GType=FpiDevicePxat`，`id=pxat_pt2887ci`，`USB IDs=2f0a:1055`，`features=0x1fe`，10 个回调全 Y → **PASS** |
| 4 | libfprint 真实枚举 `enumerate_test` | `Opening driver .../libpxat_pt2887ci.so` → `probe: PXAT PT2887-CI matched` → `libfprint discovered 1 fingerprint device(s)` → **PASS** |
| 5 | `ldd` | 依赖全部解析到系统已装的 libfprint / gusb / glib / libusb |

`make check` 把上面 4 项串成一条命令，全部通过。

### 未能在本会话完成的一步

容器进程被设置了 `NoNewPrivs: 1`，`sudo` 被拒绝，
`/dev/bus/usb/001/003` 是 `root:root 0644`，因此**拿不到 USB 写权限，
没法在本会话里真的发一帧 `a1` 并收回应答**。

所以「bulk 通信在本机 CI 固件上的实际行为」是唯一待确认项。
证据链已经很强（厂商 DLL 点名 `PT2887-CI Module` + 完整帧 + CRC + NAK 全对上，
且 libfprint 已在真机上把这个驱动绑定到该设备），但**仍建议先跑**：

```bash
sudo ./dist/pxat_probe selftest
```

若 `a1`/`1f` 都返回合法帧且 CRC 通过，即可放心 `sudo ./install.sh`。

## 七、遗留问题与建议

1. **`a2`（17 B 载荷）初始化命令未实现**。静态上像固件/参数配置，
   若 `selftest` 正常但录入异常，用 `pxat_probe raw --unsafe a2 <16 bytes>` 探测。
2. **槽位区间 10..19 是推断**（来自同厂 SS 型号实测）。
   若 `pxat_probe index` 显示占用槽位在区间外，改环境变量或调整源码常量。
3. **固件升级命令集（`CMDSET_*`）未实现**，也不需要：本机模组固件已可工作；
   刷固件风险高，且 `ACM32FP.bin` 属于另一套 OMS 模组，绝不能拿它刷本机设备。
4. **其它 5 个 PID 未纳入 `id_table`**（100B/1021/1059/100D/100E）。
   它们大概率同协议，但没有实测；为了避免误绑定到不兼容固件，
   驱动只声明本机这一个 PID。需要支持时按 PID 逐个验证再加。
5. 想进一步确认时序，可 `sudo modprobe usbmon` 抓 `1u` 总线流量，
   对照本报告的命令表逐帧比对。
